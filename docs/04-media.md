# 4. Видео, звук и время кадров

[Оглавление](../README.md) · [Границы проверки](08-validation.md)

После дешифрования первых 32 байт payload получаются:

| Смещение | Тип | Поле |
|---:|---|---|
| 0 | uint8 | quality |
| 1 | uint8 | type; 4 означает аудио |
| 2 | uint32 LE | sequence |
| 6 | uint32 LE | length полезных данных |
| 10 | int64 LE | timestamp в миллисекундах |
| 18 | uint32 LE | offset первой зашифрованной области |
| 22 | uint32 LE | block_align |
| 26 | uint32 LE | skip |
| 30 | uint8 | stream |
| 31 | byte | В этой реализации отдельно не интерпретируется |

Видео шифруется **выборочно**: после header дешифруются блоки размером
`block_align` начиная с `offset`, с пропуском `skip` байт между ними. Для audio
дешифруется начальная область `min(block_align, length)`. CBC-контекст продолжается
после header на выбранных блоках; пропущенные plaintext-области в него не подаются.
Дешифрование всего хвоста как единого CBC сообщения испортит данные.
`block_align` должен делиться на 16, `length` не может превышать payload.

На проверенной камере: HEVC codec=5; в SD наблюдалось 2304×1296.
Аудио codec=101 — IMA ADPCM, 16000 Гц, mono; код также принимает codec=100 PCM.
Атрибуты читаются из `vattr`/`aattr`, не выводятся только из размера пакета.

ADPCM-пакет начинается с signed LE int16 predictor, byte step-index (0..88),
зарезервированного байта. Далее nibble low → high. Каждый пакет начинает своё
состояние декодера; перенос состояния предыдущего пакета даёт искажения.
См. ниже алгоритм пакета; таблицы IMA ADPCM — стандартные.

## Алгоритм выборочного дешифрования

```text
decryptor = новый AES-контекст для текущего пакета (по secure type)
header = расшифровать payload[0:32] этим контекстом
data = копия payload[32:]
проверить length <= len(data), block_align кратен 16

если decryptor существует и block_align > 0:
    если type == 4:
        расшифровать data[0:min(block_align, length)] тем же контекстом
    иначе:
        position = min(offset, length)
        пока position + block_align <= length:
            расшифровать ровно block_align байт тем же контекстом
            position += block_align + skip

вернуть data[0:length]
```

При `block_align=0` дополнительных зашифрованных блоков нет.
Для secure type 0 AES не используется вообще. Для зашифрованных областей
проверяйте кратность обрабатываемой длины 16 байтам, включая аудио.
Поле `offset` отсчитывается от начала **data после 32-байтного media header**.
Контекст продолжается внутри одного media-пакета, а не через всю TCP-сессию.

## IMA ADPCM: один пакет

1. Прочитать predictor как signed little-endian int16.
2. Прочитать step-index и проверить диапазон 0..88; четвёртый байт пропустить.
3. Первым PCM-сэмплом выдать predictor.
4. Для каждого последующего байта обработать сначала low nibble, затем high nibble.
5. Для nibble `n` и шага `s`:

```text
delta = (s >> 3)
      + (s      если n & 4)
      + (s >> 1 если n & 2)
      + (s >> 2 если n & 1)
predictor += -delta если n & 8, иначе +delta
predictor = clamp(predictor, -32768, 32767)
index += [-1,-1,-1,-1,2,4,6,8][n & 7]
index = clamp(index, 0, 88)
```

Используется стандартная 89-элементная IMA step table (7…32767).
Выход — signed PCM16 little endian. Для N входных байт при N≥4 получается
`1 + 2*(N-4)` сэмплов. Каждый пакет берёт predictor/index из своего заголовка.
Не трактуйте такой пакет как произвольный непрерывный WAV/ADPCM-поток.

## Первичная проверка видео

Сохраняйте только расшифрованные видеоданные, отделив аудио и заголовки.
Для уже полученного elementary stream:

```sh
ffprobe -v error -show_streams camera.es
# Только если атрибуты/анализ подтвердили HEVC:
ffplay -f hevc camera.es
```

Для декодирования нужны корректные границы/сборка видеоданных и параметры
кодека. Дождитесь ключевого кадра и его parameter sets; наличие любого NAL-пакета
ещё не гарантирует изображение. Запрос `IDRreq=1` приведён в LIVE_START.

## Не потерять время и синхронизацию

Сырой `.es` не содержит контейнерных PTS и аудиодорожки. Сохраняйте media timestamp
рядом с каждым кадром/пакетом. При мультиплексировании выберите общую временную
базу для видео и звука и пересчитывайте миллисекунды в time base контейнера.
Обрабатывайте разрывы, переподключения и скачки времени как отдельные участки.

Подстановка постоянного FPS из предположения не сохраняет реальные пропуски
и легко вызывает рассинхронизацию. В исходном описании встречались 20 fps,
но это не универсальная частота HSC-камер. Точность wall-clock медиа-метки
проверяйте на своей прошивке; не считайте её автоматически доверенным временем.
