# 3. Relay, TCP и IOTC

[Оглавление](../README.md) · [Границы проверки](08-validation.md)

`call_channel()` отправляет подписанное тело:

```json
{
  "mr": {"params": {"access_token": "TOKEN", "device_id": 123456789, "call": 2}},
  "timestamp": 1790000000
}
```

Call types в реализованных сценариях: **2** — live, **3** — запрос SD-списка,
**5** — чтение SD-медиа. Из `mr.result` извлекаются адрес/порт:
`app_trs_ip` / `app_trs_port`, иначе `trs_ip` / `trs_port`, а также
`channel_handle`, `channel_token`.

После TCP connect отправляется ровно 1500 байт:

| Смещение | Размер | Содержимое |
|---:|---:|---|
| 0 | 4 | LE uint32, command=1100 |
| 4 | 4 | LE uint32, device ID |
| 8 | 4 | LE uint32, channel handle |
| 12 | до 36 | channel token, UTF-8, обрезка до 36 байт |
| Остаток | до 1500 | Нули |

Ответ — 64 байта. Первые два LE uint32 должны быть **1101 / 1000**.
После этого исходящие IOTC-запросы имеют 64-байтную transport-обёртку;
входящий reader данной реализации читает непосредственно 16-байтный IOTC-заголовок.
Не добавляйте лишний раз 64 байта к каждому входящему пакету.

## IOTC и управляющий JSON

Исходящий запрос:

```text
Transport[64]: uint32_le(1200), uint32_le(len(IOTC)), остальные байты 0
IOTC[16] + payload
```

| IOTC offset | Поле |
|---:|---|
| 0..3 | LE uint32 command, JSON-запрос `0x38030818` |
| 4 | Версия/флаг, в запросе 1 |
| 5 | secure type: 0 plain, 1 AES-ECB, 2 AES-CBC |
| 6 | Младший байт sid |
| 7..11 | Зарезервировано, в запросе нули |
| 12..15 | LE uint32 длины payload |

JSON содержит `id`, `chn`, `method_id`, `ts`, `params`. `_iotc_request()`
шифрует compact JSON AES-CBC с PKCS#7. Ответы JSON приходят с командами
`0x38030818` / `0x38030822`, медиапакеты — `0x38030820`.
Читать TCP нужно до точного количества байт, а не считать один recv одним пакетом.
Текущий защитный предел payload — 16 МБ.

| Метод | Значение | Назначение |
|---|---:|---|
| Key exchange | `0x30102` / 196866 | Облачный обмен ключами |
| Keepalive | `0x30200` / 197120 | Поддержание live |
| Live start | `0x30202` / 197122 | Запуск видео/звука |
| Media info | `0x30204` / 197124 | Атрибуты кодеков |
| SD list | `0x30220` | Список записей |
| SD replay | `0x30222` | Начало/пополнение передачи |
| SD info | `0x30224` | Атрибуты, конец, alive |
| Read / Write / Action | `0x30300` / `0x30302` / `0x30308` | Свойства и команды |

Запуск live:

```json
{"up":{"quality":0,"video":1,"audio":1,"IDRreq":1}}
```

Keepalive примерно каждые 4 с:

```json
{"flag":2,"tms1":0,"decode_tms":0}
```

## Чтение границ пакетов

TCP не сохраняет границы сообщений. Вызов `recv(16)` может вернуть меньше
16 байт, а один большой `recv` — захватить несколько сообщений.

```python
def recv_exact(sock, size):
    parts = bytearray()
    while len(parts) < size:
        chunk = sock.recv(size - len(parts))
        if not chunk:
            raise EOFError("TCP closed before the full packet arrived")
        parts.extend(chunk)
    return bytes(parts)
```

После 16-байтного входящего заголовка извлеките длину, проверьте её верхний
предел, затем дочитайте payload. Таймауты задавайте на соединение/операцию.
Ограничение 16 МБ — политика разобранного клиента, не установленный максимум протокола.

## Защита JSON и media — разные процедуры

| secure type | JSON payload | Media payload |
|---:|---|---|
| 0 | UTF-8 JSON без AES | Открытый 32-байтный header и данные |
| 1 | AES-128-ECB, затем PKCS#7 unpad | AES-ECB header и выбранных блоков |
| 2 | AES-128-CBC, затем PKCS#7 unpad | AES-CBC header и выбранных блоков с продолжением контекста |

JSON после расшифрования должен быть объектом. Проверьте размер AES-блоков,
padding и UTF-8 до использования полей. У media нет правила «снять PKCS#7
со всего хвоста»: следующий раздел описывает выборочное дешифрование.

IOTC передаёт младший байт sid. В наблюдавшемся live-reader допускаются
ответы с sid=0 либо sid, совпадающим с младшим байтом текущей сессии.
Это проверка соответствия сессии в данном клиенте, а не замена криптографической проверки.

Keepalive нельзя привязывать только к приходу нового кадра: при молчании
камеры таймер всё равно должен срабатывать. Успех обработки ответа оценивайте
по `result.code`; вложенная ошибка может прийти после успешного forward.
