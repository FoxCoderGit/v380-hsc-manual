# 6. Список и чтение SD-записей

[Оглавление](../README.md) · [Границы проверки](08-validation.md)

Call type 3, method `0x30220`:

```json
{"filter":11,"mode":2,"start":1790000000000,"end":1790086399999}
```

Границы — UTC epoch milliseconds для нужных локальных суток, end включительно.
`data.list[].s` — смещение от start в мс, `d` — длительность мс, `t` — тип:
1 постоянная запись, 2 события, 8 интервальная. Страницы `slice` идут по порядку,
`flag=0` завершает список. UTC-маска календаря не определяет локальное наличие
записей: файлы, пересекающие полночь, нужно учитывать с предыдущего дня.

Call type 5, method `0x30222`:

```json
{"sts":1790000000000,"pts":1790000000001,"time_id":0,"frames":100,"speed":10,"mode":2,"video":1,"audio":1,"rtype":1,"vsspec":1}
```

`sts` — абсолютное UTC-начало исходной записи, `pts` — абсолютная искомая позиция
+1 мс. К ним нельзя ещё раз прибавлять +7 часов. Значения времени в JSON выше —
условный пример, не готовая запись конкретной камеры.

В `0x30224` info_id=1 несёт атрибуты, 3 означает конец, 4 — alive.
Окно 100 считает **видео и аудио**; после 90 пакетов отправляется
`{"frames":100}`. Если считать только видео, длинная загрузка останавливается.
Для прекращения частичной загрузки используется `0x30990` именно на SD-канале;
общая live-сессия не закрывается.

**1104** — истёкшая сессия. Ответ может иметь id=0, поэтому его проверяют
до сравнения request ID. SD-читатель обновляет public key и exchange, сохраняя
ключ активного live. Повтор с новыми ключами допустим до первого кадра; после
частичной передачи задача должна начаться заново отдельным файлом, иначе
получатся повторяющиеся кадры и некорректная временная шкала.

## Разделите live и SD

У SD свой канал чтения и состояние сессии. Сериализуйте SD-операции,
чтобы ответы и окна чтения разных задач не смешивались. Обновление ключей
для SD не должно незаметно менять shared secret уже активного live-reader.
При 1104 сначала определите, к какой операции относится ошибка.

## Временные единицы

| Поле/этап | Единица |
|---|---|
| HTTP `timestamp`, IOTC JSON `ts` | Unix seconds |
| Media header timestamp | Миллисекунды согласно разобранному клиенту |
| SD `start`, `end`, `sts`, `pts` | UTC epoch milliseconds |
| SD list `s`, `d` | Смещение/длительность в миллисекундах |

Границы локального дня сначала вычисляются в выбранном IANA timezone, затем
переводятся в UTC epoch milliseconds. Не считайте любой день ровно 86400000 мс
в зонах с DST. Список может потребовать предыдущий день, если запись началась
раньше полуночи и продолжается в выбранном диапазоне.

## Контроль полноты

Файл считается пригодным не по одному признаку «получен ответ»:

1. Получены атрибуты и медиа для нужной записи/позиции.
2. Своевременно пополняется окно frames с учётом обоих типов пакетов.
3. Зафиксированы конец/причина остановки и диапазон временных меток.
4. Результат декодируется выбранным кодеком; ожидаемая длительность проверена.

Если передача была прервана и начата заново, создайте отдельный временный
результат. Склеивание повторно полученных кадров в конец старого файла
даёт дубликаты и неверное время. Поведение отдельных mode/filter/speed
значений за пределами показанных запросов в этой документации не установлено.
